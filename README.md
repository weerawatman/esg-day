# Data Guardians — Live Team Quiz

เกมควิซสดภาษาไทยแนว Kahoot สำหรับกิจกรรม Data Governance และ Data Security: **10 คำถาม · 3 ทีมสุ่ม · รหัสพนักงาน + ชื่อเล่น**

## เปิดเกม

ดับเบิลคลิก **Open-Game.cmd** หรือเข้า **http://localhost:3000** เมื่อเซิร์ฟเวอร์เปิดอยู่

วิธีเปิดผ่าน PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File .\Start-Game.ps1
```

สคริปต์เปิดเซิร์ฟเวอร์เบื้องหลังและเปิดเบราว์เซอร์ หากต้องการเปิดแบบเห็นหน้าต่างเซิร์ฟเวอร์:

```powershell
npm ci
npm start
```

ใช้ Node.js 24 ขึ้นไป ติดตั้งครั้งแรกต้องใช้อินเทอร์เน็ต หลังจากนั้นไฟล์หน้าเว็บ QR และเสียงเกมทำงานในเครื่อง ไม่มีการเรียกบริการเสียงหรือรูปภาพภายนอก

## Deploy บน Vercel

โปรเจกต์นี้รันได้ 2 แบบคนละสถาปัตยกรรม เลือกตามลักษณะงาน:

| | รันในเครื่อง/LAN (`npm start`) | Vercel (`api/*`) |
|---|---|---|
| ใช้เมื่อ | จัดกิจกรรมในสถานที่เดียว มือถือ+จอต่อ Wi-Fi เดียวกัน | อยากได้ลิงก์สาธารณะ เล่นจากที่ไหนก็ได้ |
| เก็บสถานะห้อง | ในหน่วยความจำโปรเซส + ไฟล์ `data/rooms.json` | ตาราง Postgres บน Supabase (ทุก request โหลด/บันทึกใหม่) |
| ความหน่วง | ต่ำมาก ไม่พึ่งอินเทอร์เน็ต | ขึ้นกับ Vercel + Supabase |

**`server.js`** (ใช้กับ `npm start`/`Open-Game.cmd`) กับ **`api/*.js`** (ใช้เมื่อ deploy บน Vercel) เป็นคนละทางเข้าที่ใช้ตรรกะเกมเดียวกันจาก `lib/game.js` แต่คนละชั้นเก็บข้อมูล — แก้ไฟล์ฝั่งใดฝั่งหนึ่งไม่กระทบอีกฝั่ง

### ตั้งค่าก่อน deploy

Vercel เป็น serverless (ไม่มีหน่วยความจำถาวรระหว่าง request และเขียนไฟล์ลงดิสก์โปรเจกต์ไม่ได้) จึงต้องมีฐานข้อมูลภายนอกเก็บสถานะห้องแทน ไปที่ **Project Settings → Environment Variables** ของโปรเจกต์บน Vercel แล้วเพิ่ม:

| ตัวแปร | ค่า |
|---|---|
| `SUPABASE_URL` | URL โปรเจกต์ Supabase เช่น `https://xxxxxxxx.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | คัดลอกจาก Supabase Dashboard → Project Settings → API → **service_role** (secret) — **ห้ามใส่ในโค้ดหรือส่งให้ผู้เล่น** ใช้ได้เฉพาะฝั่งเซิร์ฟเวอร์เท่านั้น |
| `ADMIN_PASSWORD` | รหัสผ่านหน้าจัดการคำถาม (`/?admin`) — บน Vercel ต้องตั้งค่านี้เอง ไม่มีการสุ่มรหัสชั่วคราวให้เหมือนตอนรันในเครื่อง |
| `PUBLIC_URL` (ถ้ามีโดเมนของตัวเอง) | เช่น `https://esg-day.example.com` ไม่ตั้งก็ได้ ระบบจะใช้โดเมน Vercel ของดีพลอยเมนต์นั้นแทน |

เพิ่มตัวแปรแล้วต้อง **Redeploy** อีกครั้ง (ตัวแปรจะมีผลกับดีพลอยเมนต์ใหม่เท่านั้น)

### ตารางใน Supabase

ทุกตารางเปิด Row Level Security โดยไม่มี policy ให้ role `anon`/`authenticated` — เข้าถึงได้เฉพาะฝั่งเซิร์ฟเวอร์ผ่าน service_role key เท่านั้น ไม่มีตัวไหนถูกอ่านกลับโดยแอป (เป็นข้อมูลไว้ให้ผู้ดูแลสืบค้นเองใน Supabase)

| ตาราง | ใช้ทำอะไร |
|---|---|
| `rooms(code, data, version)` | สถานะห้องทั้งหมดที่เกมใช้เล่นจริง (`data` คือ JSON ก้อนเดียวที่มีผู้เล่น/คำตอบ/คะแนน) — **แหล่งข้อมูลจริงของเกม** แต่อ่านตรง ๆ ยาก เพราะซ้อนอยู่ใน JSON |
| `question_bank(id, data)` | ชุดคำถาม 10 ข้อที่แก้ผ่านหน้า `/?admin` เก็บไว้แถวเดียว ใช้ตอนสร้างห้องใหม่เท่านั้น ไม่เกี่ยวกับผลการเล่น |
| `players(room_code, employee_id, name, team_id, team_name, score, bot)` | **มิเรอร์ไว้อ่านง่าย**: ใครอยู่ห้องไหน ทีมอะไร คะแนนรวมเท่าไร อัปเดตทุกครั้งที่มีคนเข้าร่วม/ตอบ/คะแนนเปลี่ยน |
| `answers(room_code, employee_id, question_id, choice, correct, voided)` | **มิเรอร์ไว้อ่านง่าย**: แต่ละคนตอบข้อไหนว่าอะไร ถูกหรือผิด ข้อนั้นถูกยกเลิกหรือไม่ |
| `team_scores` (view) | รวมคะแนน+จำนวนคนต่อทีมจากตาราง `players` ให้อัตโนมัติ ไม่ต้องคำนวณเอง |

ตัวอย่างคำสั่งดูผลใน SQL Editor ของ Supabase:

```sql
-- ใครอยู่ทีมไหนในห้อง 123456 พร้อมคะแนน
select employee_id, name, team_name, score from players where room_code = '123456' order by team_name, score desc;

-- คะแนนรวมแต่ละทีมในห้อง 123456
select * from team_scores where room_code = '123456' order by total_score desc;

-- ใครตอบข้อ 3 (question_id เริ่มที่ 0) ผิดบ้าง
select employee_id from answers where room_code = '123456' and question_id = 2 and correct = false and voided = false;
```

`players`/`answers` เป็นตารางมิเรอร์ที่แอปเขียนฝ่ายเดียว ไม่ได้อ่านย้อนกลับมาใช้เล่นเกม ถ้าเขียนไม่สำเร็จชั่วคราว (เช่นเน็ตสะดุด) จะไม่กระทบผู้เล่น แค่ข้อมูลในตารางนี้อาจตามหลังเล็กน้อยแล้ว sync ใหม่ในรอบถัดไป

### ข้อจำกัดบน Vercel

- Poll ทุก 500ms ต่อผู้เล่นจะยิง function invocation และ query ฐานข้อมูลจำนวนมากช่วงมีคนเล่นพร้อมกันหลายสิบคน เกิน free tier ได้ถ้าใช้งานหนัก/นาน
- เขียนพร้อมกันในห้องเดียวกัน (เช่น 20 คนตอบพร้อมกัน) ใช้ retry แบบ optimistic concurrency ผ่านคอลัมน์ `version` ปกติสำเร็จในไม่กี่ครั้งลองใหม่ แต่ในทางทฤษฎีอาจต้องรอสั้น ๆ ถ้าชนกันถี่มาก
- สำหรับกิจกรรมจริงหน้างานที่ต้องการความหน่วงต่ำสุดและไม่พึ่งอินเทอร์เน็ต ยังแนะนำให้รันในเครื่อง/LAN ตามหัวข้อ **เปิดเกม** ด้านบน

## ทดลองด้วยตัวเอง

กด **ลองเล่นโหมดสาธิต** เพื่อสร้างผู้เล่นจำลอง 20 คน ระบบสุ่มเป็น 3 ทีม จำนวน 7–7–6 คน เลือกเวลาแล้วเริ่มภารกิจ ระบบจำลองการตอบให้ พิธีกรกดเปิดเฉลย ลุ้นอันดับ และไปข้อถัดไป

ห้องและคะแนนจำลองมีป้าย **โหมดสาธิต / ผู้เล่นจำลอง** ชัดเจน

## เล่นจริง

1. ผู้ดำเนินกิจกรรมกด **เปิดห้องกิจกรรม** แล้ว **จอกลาง** สำหรับโปรเจกเตอร์
2. ผู้เล่นสแกน QR หรือกรอกรหัสห้อง แล้วกรอก **รหัสพนักงาน + ชื่อเล่น**
3. ระบบสุ่มให้เข้าทีม SHIELD, KEY หรือ RADAR โดยเลือกจากทีมที่มีคนน้อยที่สุด ให้จำนวนใกล้เคียงกัน มีหน้าลุ้นทีมหลังลงชื่อ
4. รหัสพนักงานเดียวเข้าได้ครั้งเดียวต่อห้อง จอกลางและข้อมูลที่ส่งให้ผู้ชมแสดงเฉพาะชื่อเล่น ไม่มีรหัสพนักงาน การลงชื่อนี้ไม่ได้เชื่อมตรวจสอบตัวตนกับบัญชีบริษัท
5. พิธีกรเลือกเวลาแต่ละข้อ **15 / 20 / 30 / 45 / 60 วินาที** ก่อนเริ่ม ค่าเริ่มต้น 20 วินาที ใช้เท่ากันทุกข้อในห้องนั้น
6. พิธีกรกด **เริ่มภารกิจ** ได้ทันทีที่พร้อม ไม่บังคับจำนวนคนหรือให้ครบทุกทีมก่อน ระบบล็อกสมาชิกและนับ **3–2–1** ก่อนเปิดทุกคำถาม
7. ช่วยกันคุยในทีม แต่ทุกคนกดตัวเลือกและ **ยืนยันคำตอบ** จากมือถือของตนเอง
8. นาฬิกาวงกลมและแถบเวลานับถอยหลัง เหลือ 5 วินาทีจะแสดงสัญญาณเร่งจังหวะ เมื่อหมดเวลาหรือทุกคนตอบครบ ระบบปิดรับคำตอบ
9. พิธีกรกด **เปิดเฉลยและให้คะแนน** ดูเหตุผลและกราฟคำตอบ แล้ว **ลุ้นอันดับทีม** เพื่อแสดงคะแนนและการเปลี่ยนอันดับ
10. กด **ไปข้อถัดไป** ทำจนครบ 10 ข้อ แล้ว **ประกาศทีมชนะเลิศ** พร้อมเอฟเฟกต์ฉลอง
11. ดาวน์โหลดผลเป็น JSON และ **เปิดห้องสำหรับกลุ่มถัดไป** คะแนนเริ่มใหม่แยกจากห้องเดิม

ผู้ใช้กด **♪ เปิดเสียง** ที่เครื่องจอกลางเพื่อเปิดเสียงเตรียมตัว เสียง 5 วินาทีสุดท้าย เสียงเฉลยและประกาศผล กด **♪ ปิดเสียง** ได้ตลอด การเปิดเสียงเป็นรายหน้า และต้องเปิดใหม่หลังรีเฟรช

## คะแนนและเนื้อหา

| ช่วง | เนื้อหา | จำนวน | ตอบถูกต่อคน |
|---|---|---:|---:|
| อุ่นเครื่องเรื่องข้อมูล | Data Governance | 4 ข้อ | 1 คะแนน |
| จับให้ทันภัยใกล้ตัว | Data Security | 4 ข้อ | 1 คะแนน |
| สองข้อชี้ชะตา | สถานการณ์ตัดสินใจ | 2 ข้อ | 1 คะแนน |

- คะแนนเต็มคนละ **10 คะแนน** (ข้อละ 1 คะแนนเท่ากันทุกข้อ) ตอบผิดหรือไม่ตอบได้ 0 ไม่มีโบนัสความเร็ว
- 20 คนสุ่มเป็น 7–7–6 คน จัดอันดับด้วย **คะแนนรวม ÷ คะแนนเต็มของทีม × 100** จึงไม่ทำให้ทีม 6 คนเสียเปรียบ จำนวนสมาชิกล็อกตั้งแต่เริ่ม
- ตัวอย่าง: ทีม 7 คนเต็ม 70 คะแนน ทีม 6 คนเต็ม 60 คะแนน หากตอบถูกทุกข้อ ทั้งสองทีมได้ 100% และเป็นแชมป์ร่วม
- หน้าลุ้นอันดับแสดงเปอร์เซ็นต์สำหรับทีมขนาดต่างกัน พร้อมคะแนนรวมจริงประกอบ
- ก่อนเริ่ม พิธีกรย้ายทีมจากรายชื่อได้ หากมีเหตุจำเป็น หลังเริ่มย้ายไม่ได้
- ก่อนเปิดเฉลย พิธีกร **ยกเลิกข้อนี้** ได้เมื่อเกิดปัญหา ทุกคนได้ 0 ในข้อนั้น ไม่มีการหักแต้มที่ได้จากข้ออื่น
- ระบบเคารพการตั้งค่าลดการเคลื่อนไหวของอุปกรณ์ และใช้ทั้งสี รูปทรง และตัวอักษร A–D กำกับคำตอบ

## มือถือและเครือข่าย

**localhost ใช้เฉพาะเครื่องเปิดเซิร์ฟเวอร์** มือถือใช้ IP ของเครื่องนี้ผ่าน QR เช่น `http://172.16.6.160:3000` ต้องเชื่อมเครือข่ายที่เข้าถึงกันได้ และเปิดเครื่องเซิร์ฟเวอร์ค้างไว้โดยไม่เข้าโหมดพัก

ตรวจ QR ด้วยมือถือก่อนวันงาน ในหน้า **ลิงก์สำหรับมือถือ / ตั้งค่าเครือข่าย** เปลี่ยน IP ได้เมื่อมี VPN หรือหลายเครือข่าย หาก Wi-Fi แยกอุปกรณ์หรือ Firewall บล็อกพอร์ต ให้ผู้ดูแลเครือข่ายเปิดการเข้าถึง Node.js / พอร์ตที่ใช้ตามนโยบายองค์กร

เกมนี้ยังไม่ได้เผยแพร่บนอินเทอร์เน็ต หากนำขึ้นใช้งานสาธารณะ ต้องจัดการ HTTPS การจำกัดคำขอ และสิทธิ์สร้างห้องให้เหมาะสม

## การกลับเข้าเล่นและข้อมูลเก่า

- รีเฟรชกลับเป็นผู้เล่นคนเดิมได้ในเบราว์เซอร์และที่อยู่เว็บเดิม ทีมและคะแนนไม่เปลี่ยน
- ถ้าลงชื่อสำเร็จที่เซิร์ฟเวอร์แต่เครือข่ายหลุดก่อนรับผล ให้ลงชื่อด้วยข้อมูลเดิมในเบราว์เซอร์เดิมอีกครั้ง ระบบใช้รหัสคำขอเฉพาะเพื่อคืนเซสชันเดิมโดยไม่เพิ่มสมาชิกซ้ำ
- เบราว์เซอร์อื่นไม่สามารถรับสิทธิ์ผู้เล่นเดิมด้วยรหัสพนักงานเพียงอย่างเดียว
- สิทธิ์พิธีกรเก็บในเบราว์เซอร์ที่สร้างห้อง หน้าแรกมี **กลับห้องล่าสุด** อย่าล้างข้อมูลเบราว์เซอร์ระหว่างกิจกรรม
- ห้องเวอร์ชันเดิมที่มี 12 คำถาม / 4 ทีมยังเก็บกติกาและคะแนนเดิมไว้ **เปิดห้องใหม่เพื่อเล่นแบบ 10 ข้อ / 3 ทีม**
- ห้องใหม่บันทึกชุดคำถามและกติกาของตัวเอง การแก้ไฟล์คำถามภายหลังไม่เปลี่ยนคำตอบของห้องที่สร้างแล้ว
- ทุกครั้งที่ **เปิดห้องสำหรับกลุ่มถัดไป** ระบบสุ่มลำดับคำถามใหม่ภายในแต่ละช่วง (อุ่นเครื่อง / จับภัย / สองข้อชี้ชะตา) ให้อัตโนมัติ ยังเป็นชุด 10 ข้อเดิม เพียงสลับลำดับ ทีมก็สุ่มใหม่ตามผู้เล่นที่สแกนเข้าห้องใหม่
- ผลห้องเก็บใน `data/rooms.json` รวมรหัสพนักงานและรหัสสิทธิ์เฉพาะผู้ดูแล ไม่แชร์ไฟล์นี้กับผู้เล่น เก็บและลบข้อมูลตามความจำเป็นของกิจกรรม
- ไฟล์ผลที่ดาวน์โหลดมีเฉพาะชื่อเล่น ทีม และคะแนน ไม่ส่งออกรหัสพนักงาน
- เปิดเซิร์ฟเวอร์ใหม่ยังอ่านผลเดิมได้ เวลาที่เซิร์ฟเวอร์ปิดยังนับเป็นเวลาของคำถามที่เปิดค้างอยู่

## ปรับเนื้อหาและตั้งค่า

### แก้ผ่านหน้าเว็บ (แนะนำ)

เข้า **http://localhost:3000/?admin** หรือกดลิงก์ **จัดการคำถาม** ที่หน้าแรก กรอกรหัสผ่านผู้ดูแล แล้วแก้คำถาม ตัวเลือกทั้ง 4 ข้อ คำตอบที่ถูก และคำอธิบายของ 10 ข้อเดิมได้ทันที กด **บันทึกทั้งหมด** เพื่อเก็บลง `data/questions.json` หรือ **คืนค่าเริ่มต้น** เพื่อกลับไปใช้ชุดคำถามในไฟล์ต้นฉบับ

- แก้ได้เฉพาะเนื้อหา (ข้อความ/ตัวเลือก/คำตอบ/คำอธิบาย) จำนวนข้อ โครงสร้าง 3 รอบ (4/4/2) และคะแนน (ข้อละ 1 คะแนนเท่ากันทุกข้อ) คงเดิมเสมอ
- มีผลเฉพาะ **ห้องที่เปิดใหม่หลังบันทึก** ห้องที่กำลังเล่นหรือจบไปแล้วไม่เปลี่ยนตาม
- รันในเครื่อง: บันทึกลง `data/questions.json` ตั้งรหัสผ่านด้วย `$env:ADMIN_PASSWORD = 'รหัสของคุณ'` ก่อน `npm start` ถ้าไม่ตั้งไว้ ระบบจะสุ่มรหัสชั่วคราวและพิมพ์ไว้ที่หน้าต่างเซิร์ฟเวอร์ทุกครั้งที่เปิด
- บน Vercel: บันทึกลงตาราง `question_bank` ใน Supabase ต้องตั้ง `ADMIN_PASSWORD` เองในตัวแปรแวดล้อมของโปรเจกต์ (ดูหัวข้อ **Deploy บน Vercel**)

### แก้ผ่านไฟล์

แก้ `lib/questions.js` แล้วเปิดเซิร์ฟเวอร์ใหม่ จากนั้น **สร้างห้องใหม่** คำตอบถูกใช้ดัชนี 0=A ถึง 3=D ปรับคำศัพท์บทบาทและช่องทางรายงานเหตุให้ตรงกับองค์กร แหล่งเนื้อหาทั่วไปอยู่ในข้อเสนอต้นฉบับ `Data-Guardians-Game-Proposal.md` ซึ่งบันทึกรูปแบบเวอร์ชันแรก การแก้ไฟล์นี้เป็นค่าเริ่มต้นที่ปุ่ม **คืนค่าเริ่มต้น** จะย้อนกลับไปใช้

```powershell
$env:PORT = '3000'
$env:PUBLIC_URL = 'http://172.16.6.160:3000'
$env:ADMIN_PASSWORD = 'รหัสผ่านหน้าจัดการคำถาม'
npm start
```

ค่าลิงก์ที่ตั้งในหน้าเว็บจะมีผลก่อน PUBLIC_URL ในเบราว์เซอร์นั้น

## การทดสอบ

```powershell
npm test
npm run test:browser
```

Browser test ต้องเปิดเซิร์ฟเวอร์และมี Microsoft Edge ทดสอบผู้เล่น 20 เซสชันจากเครื่องเดียว รวมถึงรหัสพนักงานซ้ำ การตอบซ้ำ/หมดเวลา การสุ่มทีม กติกาห้องเก่า การลงชื่อเมื่อผลตอบกลับสูญหาย หน้า 3–2–1 การนับเวลา และการเล่นครบ 10 ข้อบนหน้าจอคอมและมือถือ ภาพตรวจสอบอยู่ใน `output/playwright/`

ยังต้องทดสอบโทรศัพท์จริงและ Wi-Fi หน้างานก่อนกิจกรรม
